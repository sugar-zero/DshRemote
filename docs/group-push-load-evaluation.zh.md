# 推送对服务器的负担评估 & 是否要做限流（决策参考）

> 2026-11-01 · 分支 `feat/group-service` · 关联
> [`group-push-routing-options.zh.md`](group-push-routing-options.zh.md)（O1/O2/R2 方案）
> 目标：判断官方 hub（以及 relay）在正常/异常流量下的资源占用，决定限流是否必要、做到什么程度。

## 1. 一次推送在服务端到底做什么

| 路径 | 服务端工作 |
|---|---|
| O1（relay 转发 hub） | 主机 → relay 复用**已建立的 WSS**（无新端口）→ relay 校验 + 一次 HTTPS 请求 → hub（TLS 握手、JWT/Bearer 校验、限速计数、APNs 发送） |
| R2（主机直连 hub） | 主机 → hub HTTPS（TLS 握手、JWT credential 验签、配额计数、APNs 发送）；**每次推送一条小请求** |

单次 hub 请求的 CPU 量级（Node，x86/ARM 小 VPS）：

- TLS 握手：~0.1–0.5 ms（HTTP/2 keep-alive 可摊销；推送稀疏时多数是新建连接）
- JSON 解析 + schema 校验：~0.02–0.1 ms
- JWT/credential 验签（ES256/Ed25519）：~0.05–0.5 ms
- 配额计数（内存 Map）：< 0.01 ms
- APNs 发送：**异步 I/O**，不占 CPU；每个 token 一次 HTTP/2 请求（当前实现每 token 新建连接，
  延迟 50–300 ms，但并发低时无影响）
- 总计：**单请求 CPU 约 0.2–1 ms、内存约几 KB、带宽约 1–2 KB**

## 2. 正常流量估算（按产品定位：3–20 人小群体）

假设：20 台主机（每台 1–3 台手机）；每用户每天 10–200 次推送意图（turn/end + ask_user_question，
host 侧已有 30s/会话冷却、callId 去重）。

| 指标 | 低 | 典型 | 高峰（连续 agent） |
|---|---|---|---|
| 推送意图/天（全站） | 200 | ~1,000 | ~4,000 |
| 平均 QPS | 0.002 | 0.012 | 0.05 |
| 峰值 QPS（按 host 2–6/min 估） | — | 1–2 | 6–12 |
| APNs 请求/s（每 host 1–3 设备） | — | 1–6 | 18–36 |
| 带宽 | < 1 KB/s | ~10 KB/s | ~50 KB/s |
| hub CPU 占用（1 vCPU 基準） | ≈0% | < 1% | < 5% |
| hub 内存 | < 100 MB（Node 常驻） | 同左 | 同左 |
| 持久化存储 | 无（credential 无状态、配额计数内存） | 同左 | 同左 |

结论：**正常使用下，一台 1 vCPU / 512MB–1GB 的小容器绰绰有余**；relay 侧（O1）新增的只是
“收到 push.send 后转发一次 HTTPS”，相对隧道流量可以忽略。

## 3. 没有限流时的风险（真正需要限流的理由）

正常流量不是风险；风险来自**异常/滥用**：

1. **凭据泄露或恶意主机**：R2 的 credential 分发到每台主机/每台设备；一旦某台机器被入侵，
   或用户自己写脚本刷，单凭据即可向 hub 打高频请求 → TLS/JWT 校验 CPU 打满小 VPS、
   APNs 连接被打爆（Apple 会对 provider token/连接做限流，返回 429 `TooManyRequests`）。
2. **enroll 接口滥用**：R2 的 `/v1/enroll` 是公网入口，若无限速，攻击者可批量登记假设备，
   消耗内存/配额（即使 token 无效，也占请求与存储/限流状态）。
3. **误触发/循环**：多会话并发、子代理、自动化循环可能在短时间产生大量 turn/end；
   虽然 host 有 30s 冷却，但多会话叠加仍可能超出预期。
4. **用户被刷通知**：同一设备高频推送会打扰用户、影响 App 口碑；APNs 侧也会返回
   `TooManyRequests`/`Unregistered` 等。
5. **成本**：APNs 本身不收费，但 CPU/带宽/被 Apple 限流的运维成本会上升；hub 若被打挂，
   所有用户一起没有推送。

## 4. 建议的限流方案（轻量，够用即可）

不做复杂分布式限流；沿用现有 relay 的滑动窗口实现即可，配置化默认值：

| 层级 | 建议默认 | 说明 |
|---|---|---|
| per device credential | 6 次/分钟、120 次/天 | R2 主机直连的 unit；超限 429 + Retry-After |
| per host | 30 次/分钟 | 同一 host 多设备共享；防止单主机刷 |
| 全局 | 120 次/分钟（可调） | 小群体兜底；VPS 被打时保留恢复能力 |
| enroll | 5 次/小时/device、20 次/小时/IP | 防批量注册；可选 App Attest |
| 请求体 | ≤ 16 KB | 现有 |
| tokens/请求 | ≤ 20 | 现有 |
| 内容 | 只允许 `kind/host/tokens`，固定通用文案 | 现有 |

补充措施：

- **host 侧已有**：30s/会话冷却、`ask_user_question` 按 callId 去重、子代理跳过；无需改。
- **nginx/边缘**：对 `/v1/enroll`、`/v1/push` 做 IP 级粗限速与连接数限制（第一层便宜防御）。
- **去重/折叠**：保留现有 `apns-collapse-id`（同会话折叠），避免重复横幅。
- **失败语义**：429 直接返回、不重试；APNs 410 才 prune；配置错误不删 token（现有行为）。
- **可观测**：计数/429 命中/APNs 错误率指标或日志汇总；key/credential 异常告警。
- **不要过度设计**：当前规模不需要 Redis/集群限流；内存计数器重启清零可接受，
  多实例时再换共享存储。

## 5. 结论

- **正常负载**：20 人规模下推送对服务器负担极小（CPU < 5%、带宽 < 50 KB/s、无持久化），
  不做限流也“跑得动”。
- **但限流仍然必要**：目的不是省资源，而是 **防止凭据泄露/恶意刷/误循环打爆 APNs 与小 VPS、
  保护用户不被刷通知**；实现成本低（复用现有滑动窗口 ~ 几百行内含测试），建议 v1 就带。
- **优先级**：R2 的 enroll 限速 + per-device/per-host 推送限速必须做（已实现）。
  其他（App Attest、连接复用、Redis）按需后续再加。
